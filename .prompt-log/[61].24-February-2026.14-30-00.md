## Point OF AI Response

### Root Cause Analysis (from alphaTab d.ts)

Investigated the alphaTab type definitions to determine the exact conventions:

1. **`Note.string`**: "1 is the lowest string on the guitar and the bottom line on the tablature" → 1-based from LOWEST/THICKEST
2. **`Staff.tuning` / `stringTuning`**: "first item is the most top tablature line" → HIGH-to-LOW (thinnest first)
3. **`Beat.playbackStart`**: "timeline position within the current bar" → bar-relative ✓

### Three Bugs Fixed

**Bug 1: Tuning array incorrectly reversed**
- `staff.tuning` is already HIGH-to-LOW (matching our `STRING_TUNING` format)
- The code was reversing it to LOW-to-HIGH, causing D2 (lowest string) to display at the TOP of the grid instead of E4 (highest)
- Fix: Removed `.reverse()` call

**Bug 2: String mapping inverted**
- `note.string = 1` = lowest/thickest, but code treated it as highest with `stringIndex = note.string - 1`
- Fix: Changed to `stringIndex = tuning.length - importedString`
- Example: note.string=3 (D3, 3rd from lowest) → stringIndex = 6-3 = 3 → tuning[3] = D3 ✓

**Bug 3: Grid resolution too fine (16 steps instead of 8)**
- `minPlaybackDuration` scan included rest beats and grace notes, which have short durations
- This caused sixteenth-note resolution (240 ticks) when the piece only needs eighth-note (480 ticks)
- Fix: Filter `beat.isRest`, `beat.graceType !== 0`, and empty beats from the scan
- Result: Canon correctly gets 8 grid steps per 4/4 bar

### Impact
- Grid now displays strings in correct tab order (E4/high e at top, like standard TAB notation)
- Grid resolution matches actual rhythmic content (no wasted empty columns)
- alphaTeX output (`\tuning`, string numbers) consistent with corrected data
